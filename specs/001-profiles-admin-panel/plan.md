# Implementation Plan: Profiles Admin Panel

**Branch**: `001-profiles-admin-panel` (spec directory; work happens on the
current git branch `feature/django-refactor`) | **Date**: 2026-07-28 |
**Spec**: [spec.md](./spec.md)

**Input**: Feature specification from `/specs/001-profiles-admin-panel/spec.md`

## Summary

Give platform administrators a Django admin surface for the profiles domain:
a dedicated screen for the controlled `Skill` vocabulary, and freelancer/client
profiles edited **inside the account screen they belong to** rather than on
screens of their own.

The work is almost entirely admin-layer configuration over models that already
exist. It adds no dependency, no field and no migration. Three things need real
code: refusing removal of a skill that profiles still refer to (FR-028, which
`on_delete=PROTECT` does **not** cover because the relation is many-to-many),
refusing profile creation on an account being saved as inactive (FR-029, a new
`clean()` branch on both profile models), and adding a profile-presence
indicator and skill filters to the two account lists without introducing an N+1.

Structure follows the pattern `accounts/admin.py` already established
(`BaseAccountAdmin` + `StatusBadgeMixin`, recorded in `ARCHITECTURE.md`): the
profile inlines and the list-column mixin live in `accounts/admin.py` beside the
admins that own them; `profiles/admin.py` holds `SkillAdmin`, the only registered
screen this feature adds.

## Technical Context

**Language/Version**: Python 3.14

**Primary Dependencies**: Django 6.0.7 — `django.contrib.admin` only. No new
package. DRF and drf-spectacular are **not installed** and are not needed: the
deliverable is admin screens, not an API.

**Storage**: PostgreSQL 17 via psycopg 3.3.4. Schema unchanged — no migration is
generated by this feature.

**Testing**: pytest 9.1.1 + pytest-django 4.12.0, run as
`docker-compose exec web pytest`. `pytest.ini` sets `--no-migrations`, so
`profiles/migrations/0002_seed_skills.py` does not run and tests create their own
`Skill` rows.

**Target Platform**: Linux container (`docker-compose exec web`), working
directory `django_version/`.

**Project Type**: Django monolith. This feature touches the admin layer plus two
`clean()` methods. No view, no URL, no template, no serializer.

**Performance Goals**: `list_per_page = 25` throughout. The profile-presence
column must add **zero** per-row queries — it is annotated once in
`get_queryset()`, not resolved per row (research.md R-006).

**Constraints**: No new dependency. No model field and no migration
(research.md R-002, R-010). No PII in any log line or error message
(Principle VII). Every existing account-administration test must still pass,
except where FR-024 names the change as intended (SC-009).

**Scale/Scope**: Skill vocabulary in the hundreds (30 seeded), profiles in the
thousands. One registered admin added, two inlines, one mixin, one filter, two
`clean()` branches.

### Decisions taken by the human, 2026-07-28

1. **FR-021 narrowed for the skill screens.** `Skill` has no `created_at` /
   `updated_at` and orders by `["category", "name"]`, so FR-021's timestamp and
   most-recent-first clauses are unsatisfiable as written. Narrowed to apply only
   where the model carries those fields; **no field added, no migration**.
   (research.md R-002)
2. **File layout.** Profile inlines and the list mixin in `accounts/admin.py`;
   `SkillAdmin` alone in `profiles/admin.py`. `accounts.admin` imports
   `profiles.models`, never `profiles.admin`. (research.md R-001)
3. **FR-029 owned by the model.** Enforced in `FreelancerProfile.clean()` and
   `ClientProfile.clean()`, not in a form or formset — a profile-vs-account
   invariant belongs to the model under Principle VIII, and the FK is readable on
   the unsaved instance carrying the value being saved. (research.md R-003)

### Verification gates (Principle VI) — confirm before relying on them

These behaviors are asserted from Django's documented mechanisms but must be
confirmed against the pinned 6.0.7 during implementation. Each has a recorded
fallback, so neither can block delivery.

- **`list_filter` across a reverse `OneToOneField` then a `ManyToManyField`**
  (`profile__skills`). Fallback: `SimpleListFilter` over the same lookup.
  (research.md R-007)
- **`get_deleted_objects()` reached by both `_delete_view` and the
  `delete_selected` action, refusing when `protected` is non-empty.** Fallback:
  a custom bulk action replacing `delete_selected` on `SkillAdmin`.
  (research.md R-004)

**Structure Decision**: The existing two-app Django layout under
`django_version/` is kept as is. No new app, no new package beyond
`profiles/tests/admin/`. Placement of each new class follows research.md R-001:
an inline is a component of its parent screen and lives with that screen in
`accounts/admin.py`; a registered screen lives with the app that owns its model,
so `SkillAdmin` lives in `profiles/admin.py`. This mirrors the base-class +
opt-in-mixin composition already documented in `ARCHITECTURE.md` under *Django
Admin — Shared Behavior via Base Class and Mixin*.

Spec artifacts stay at the monorepo root per `CLAUDE.md`; every command they
trigger still runs inside Docker.

**Note on `test_client_profile.py`** *(revised 2026-07-31)*: when this plan was
written, `ClientProfile` had **no test module at all** and its existing
`company_name_empty` and `max_budget_not_positive` rules were untested. The human
closed that gap ahead of implementation (commit `8df77d4`), so the module now
exists and covers both rules. This feature therefore **extends** it with the
`profile_for_inactive_account` branch it adds (Principle IX) rather than creating
it. See research.md R-009.

## Implementation phasing

Ordered by the spec's own story priorities, so each step is independently
demonstrable.

| Step | Delivers | Stories | Key requirements |
|---|---|---|---|
| 1 | `SkillAdmin` — list, search, category filter, fieldsets, create/edit | US1 (P1) | FR-001..005, FR-021 |
| 2 | Skill removal: allowed when unused, refused with a count when in use, both routes | US1 (P1) | FR-027, FR-028, SC-010 |
| 3 | `profile_for_inactive_account` on both profile `clean()` methods | US2/US3 foundation | FR-029, FR-030, FR-031 |
| 4 | `BaseProfileInline` + `FreelancerProfileInline` on `FreelancerAdmin` | US2 (P2) | FR-006..010, FR-023, FR-026, FR-032, FR-036 |
| 5 | `ClientProfileInline` on `ClientAdmin` | US3 (P3) | FR-013..017 |
| 6 | Regression pass on account administration | US4 (P4) | FR-020, FR-024, SC-009 |
| 7 | `ProfilePresenceMixin` — badge + `HasProfileFilter` on both lists | US5 (P5) | FR-033..035, SC-011 |
| 8 | Skill filters on both account lists | US6 (P6) | FR-037..039, SC-012 |

Step 3 precedes steps 4 and 5 because the inlines surface a rule that must
already exist. Steps 7 and 8 touch the same two `list_filter` tuples and are
naturally delivered together, as the spec anticipates (spec.md:205-206).

Each step ships with its tests before it is considered done (Principle IX).
Test structure, fixtures, `@pytest.mark.django_db` placement and assertion style
are governed by `.claude/rules/testing.md` — notably: assert on the
`ValidationError` **code**, never the message; assert the field key is in
`error_dict` first; and remember `--no-migrations` means no seeded skills.
