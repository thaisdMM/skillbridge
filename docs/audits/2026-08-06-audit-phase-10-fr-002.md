The implementation matches the tasks and both ADRs. `clean()` raises the right

## Issues — action required

### Issue 1 — `clean()` lowercases in Python, the constraint lowercases in PostgreSQL; on a name where the two disagree, the field-level error FR-002 requires is not produced

**Where**: `django_version/profiles/models/skill.py:135-140` — the lookup
annotates `Lower("name")` (evaluated by PostgreSQL) and compares it against
`self.name.lower()` (evaluated by CPython).

**Rule violated**: *CROSS-LAYER CONSISTENCY* in `AUDITOR.md` — model-level
constraint logic and `clean()` logic must agree. It also defeats the stated
Decision Outcome of `docs/adr/case-insensitive-skill-name-uniqueness.md`: the
constraint exists as a backstop precisely because *"the constraint alone cannot
put the error beside the name field"*.

**Why it matters**: PostgreSQL's `lower()` is a per-character mapping;
CPython's `str.lower()` performs full Unicode case mapping and can change
string length. They diverge. Measured against this project's development
database on 2026-08-06:

| input | `SELECT lower(…)` | `str.lower()` | |
|---|---|---|---|
| `İ` (U+0130) | `'i'` | `'i̇'` (U+0069 U+0307) | **differ** |
| `ẞ`, `ß`, `I`, `i`, `K`, `k` | — | — | same |

Reproduced end to end, in a rolled-back transaction, with an existing skill
named `I` and the candidate `İ`:

- `full_clean()` did **not** raise `skill_name_duplicate` — the Python-lowered
  `'i̇'` never matches the database-lowered `'i'`;
- `validate_constraints()` then caught it and filed it under `__all__`:
  `{'__all__': [ValidationError(['Constraint “skill_unique_name_case_insensitive”
  is violated.'])]}` — the `NON_FIELD_ERRORS` routing the ADR documents as the
  reason a constraint alone is not viable;
- `.save()` on a path that skips `full_clean()` raised
  `IntegrityError: duplicate key value violates unique constraint
  "skill_unique_name_case_insensitive"`.

Data integrity is never at risk — the constraint holds in every case. What is
lost on this input is exactly the guarantee `clean()` was added for: a message
beside the `name` field. In the admin the operator gets a top-of-form
non-field error; on an import path, a raw `IntegrityError`.

Likelihood is low for a curated vocabulary of English-language skill names.
Severity is contained. It is reported because the audit asked for any input
where the two layers could disagree, and one exists.

**Direction**: make both sides of the comparison use the same lowercasing
function — lowercase the candidate in the database rather than in Python, so
`clean()`'s lookup is evaluated by the same expression the constraint indexes
(`django.db.models.functions.Lower` over a `Value`, mirroring the `Lower("name")`
already declared in `Skill.Meta.constraints` at `skill.py:75-79`). No
equivalent exists in `Freelancer`'s two-layer pattern to copy from: its backstop
is a boolean `CheckConstraint`, so no function is applied to a value on either
side. If the finding is accepted, the *Consequences* list of
`docs/adr/case-insensitive-skill-name-uniqueness.md` is the right place to
record it.

### Issue 2 — the edit path of the duplicate rule has no test; restricting the check to creation leaves the suite green

**Where**: `django_version/profiles/tests/models/test_skill.py:74-96` and
`:138-147`. All four tests that expect `skill_name_duplicate` build an
**unsaved** instance (`pk is None`). No test renames a **saved** skill onto a
name a **different** saved skill already carries.

**Rule violated**: `testing.md`, *A test must fail if the behavior under test is
removed*. Mentally delete the branch for the saved case — for example, guard the
whole lookup with `if self.pk is None:` — and every test in the file still
passes: the four duplicate tests use unsaved instances, and the two
self-exclusion tests expect success anyway.

**Why it matters**: the admin change form is the path FR-002 exists to guard,
and it is the saved path. The uncovered scenario is also the only one where
`.exclude(pk=self.pk)` does real work against a *foreign* row, which is where the
self-exclusion and the duplicate rule interact.

The production code is correct — verified in a rolled-back transaction: with
`ZzzAlpha` and `ZzzBeta` saved, renaming `ZzzBeta` to `zzzalpha` returned
`{'name': ['skill_name_duplicate']}`. This is a coverage gap, not a defect.

**Direction**: one model-path test alongside the two self-exclusion tests at
`test_skill.py:99-117`, following the same shape they already use (create,
mutate `name`, `full_clean()`, assert the key then the code, per `testing.md`'s
two-step `ValidationError` pattern). T078 would also reach this case through the
admin form, but T078 is deliberately out of scope and the gap is on the model
path, where the sibling tests already live.

### Issue 3 — `.distinct()` on the `ClientProfile` aggregate is not covered; deleting it breaks no test

**Where**: `django_version/profiles/admin.py:98` (the `ClientProfile` half of
`_count_referring_profiles`), against
`django_version/profiles/tests/admin/test_skill_admin.py:145-163`.

**Rule violated**: `testing.md`, *A test must fail if the behavior under test is
removed*, and the F-4 contract in `contracts/admin-surface.md` §1, which
prescribes `.distinct()` on **both** aggregates.

**Why it matters**: `test_get_deleted_objects_counts_a_profile_referring_to_several_selected_skills_once`
— the test written for F-4 — attaches all three selected skills to a
**freelancer** profile only. The `ClientProfile` aggregate returns `0` whether or
not `.distinct()` is present, so the client half of the fix is asserted nowhere.
`test_get_deleted_objects_summarizes_several_referring_profiles_in_one_entry`
does involve a client profile but uses a **single** skill, the case where
references and profiles are equal by construction — the same blind spot that let
F-4 survive T018 in the first place, now reproduced on the other model.

**Direction**: the mirror of the existing test, with the several selected skills
attached to `client_profile.interests` instead of `freelancer_profile.skills`.
Both fixtures already exist in `profiles/tests/conftest.py`.

### Issue 4 — the two `__repr__` tests state a distinction in their docstrings that neither one asserts

**Where**: `django_version/profiles/tests/models/test_skill.py:20-26` and
`:29-38`. Pre-existing — untouched by Phase 10 — but in an audited file and of
exactly the class of defect this audit was asked to hunt.

**Rule violated**: `testing.md`, *Docstrings in tests* ("describe the behavior
being verified") together with *A test must fail if the behavior under test is
removed*.

**Why it matters**: the docstrings say the unsaved instance "renders category as
the TextChoices enum" and the reloaded one "renders category as a plain string".
That difference is the only reason two tests exist. Neither asserts it: both
build the expected string with `{skill.category!r}` / `{reloaded_skill.category!r}`
— the value under test interpolated into its own expectation. If `__repr__`
stopped distinguishing the two, or if reload behavior changed, both tests still
pass. Verified on the pinned stack: `repr(Skill.Category.TECHNOLOGY)` is
`Skill.Category.TECHNOLOGY`, and the unsaved `repr` is
`Skill (id=None, name='Python', category=Skill.Category.TECHNOLOGY)` — the
literal both docstrings are talking about and neither test contains.

**Direction**: either assert the rendered form literally, so the claimed
difference is the thing that fails, or collapse the pair into one test and drop
the claim. The sibling file's `test_freelancer_profile_repr_representation`
(`test_freelancer_profile.py:91-99`) has the same derived-expectation shape and
would inherit whichever choice is made — it makes no claim its assertion does not
cover, so it is not itself a finding.

### Issue 5 — the `conventions.md` rule on `@pytest.mark.django_db` for `Skill` is over-broad and contradicts two tests that must stay marker-free

**Where**: `.claude/rules/conventions.md`, *Established invariants*, the
`skill_name_duplicate` entry: *"this `clean()` issues a queryset lookup, so a
test calling `Skill.clean()` or `Skill.full_clean()` needs
`@pytest.mark.django_db`."*

**Rule violated**: internal consistency with T077's repair 2, which states the
opposite for two named tests — *"The other two `clean()` tests stay marker-free
and must remain so."*

**Why it matters**: `test_skill_clean_empty_name_raises_validation_error`
(`test_skill.py:56`) and `test_skill_clean_none_name_passes_validation`
(`test_skill.py:66`) call `clean()` and correctly carry no marker: the empty-name
branch raises before the lookup, and the `None` branch never reaches it.
`conventions.md` is auto-loaded into every session, and as written it instructs a
future session to add markers to both — which `testing.md`'s own *Common mistakes
to avoid* table lists as a mistake ("Applying `@pytest.mark.django_db` to every
test"). The condition is "reaches the duplicate lookup", not "calls `clean()`".

**Direction**: qualify the clause to the branch that issues the query. The
existing entries in that list already carry this kind of precision (the
`freelancer_no_inactive_available` entry distinguishes the `clean()` path from
the constraint path). Per the same file's own rule, no task or requirement ID
belongs in the wording.

### Issue 6 — `unique=True` on `Skill.name` is no longer guarded by any test, and this change is what retired the guard

**Where**: the field declaration at
`django_version/profiles/models/skill.py:54-62`, against
`django_version/profiles/tests/models/test_skill.py:138-147` and `:150-167`.

**Rule violated**: `testing.md`, *A test must fail if the behavior under test is
removed*. `unique=True` staying on the field is also a listed *Decisions already
taken — do not reopen* item in Phase 10, and T075's gate exists specifically to
catch an `AlterField` that drops it.

**Why it matters**: before this change, `test_skill_name_uniqueness` asserted
`code == "unique"` — the field-level unique was the thing that produced that
code, so the test failed if `unique=True` were removed. T077's repair 1 changed
the assertion to `skill_name_duplicate`, which was necessary and correct: the
code genuinely became unreachable. But it was the only test that touched
`unique=True`, and nothing replaced it.

What remains is `test_skill_name_uniqueness_enforced_at_database_level`, which
asserts `pytest.raises(IntegrityError)` and nothing about which constraint
raised. Verified in a rolled-back transaction on 2026-08-06: an exact duplicate
currently reports `duplicate key value violates unique constraint
"skills_name_key"` — the field-level index — but
`skill_unique_name_case_insensitive` rejects that same input on its own, as
`test_skill_case_insensitive_name_uniqueness_enforced_at_database_level` already
proves for a case variant. So the assertion holds either way: **remove
`unique=True` from the field and the entire suite stays green**, on a decision
the phase marks as not reopenable.

**Direction**: `testing.md`'s *Database access in tests* lists field-metadata
introspection as a test shape that needs no database — that is the cheap guard
for a field declaration, and it keeps the assertion off PostgreSQL's constraint
naming, which is not a project contract. The alternative, asserting the
constraint name inside the `IntegrityError`, couples the test to the database's
own naming and is the weaker option.

### Issue 7 — `Skill.name`'s `max_length=100` has no boundary test, against established project practice

**Where**: `django_version/profiles/models/skill.py:54-62`. Nothing in
`test_skill.py` exercises a name at or over 100 characters.

**Rule violated**: `CLAUDE.md` Rule 8, *Follow existing patterns* — the project
already tests exactly this, on the same kind of declaration.

**Why it matters**: `profiles/tests/models/test_base.py:33-51` tests
`Profile.bio` at **exactly 500** (passes) and at **501** (raises `max_length` on
the `bio` key), and `testing.md` uses that second test as its worked example
under *Docstrings in tests*. `Skill.name` is the field an administrator types
into on the one screen this feature adds, and its limit is asserted nowhere: the
100 could be changed to 10 or to 1000 without a single test noticing.

**Direction**: the pair in `test_base.py:33-51`, transposed to `name` at 100 and
101, asserting the key then the `max_length` code per `testing.md`'s two-step
pattern. Note that a 101-character name reaching `clean()` would now also issue
the duplicate lookup, so the marker rules of Issue 5 apply.

## Open Decisions — user choice needed

### OD-1 — `test_counting_referring_profiles_issues_two_queries_for_a_selection_of_three_skills` calls the private `SkillAdmin._count_referring_profiles`

**Where**: `django_version/profiles/tests/admin/test_skill_admin.py:166-181`.

No project convention covers testing a private helper, and the test is not
tautological — a per-skill implementation would issue six queries and fail it.
Three viable options, with the measurements that separate them (taken on the
development database, 2026-08-06):

**A — keep the private call.** The assertion stays exactly two queries and stays
pinned to the helper the F-6 fix created. Cost: the test depends on a name with a
leading underscore, so an internal refactor that inlines or renames the helper
breaks a test that is not about the public behavior.

**B — route through `get_deleted_objects()`.** Measured total on the public
path: **4 queries** for a selection of 1, 3, 5 and 10 skills — flat, so a fixed
budget is expressible today. Cost: two of the four belong to Django's
`NestedObjects` collector inside `super().get_deleted_objects()`. The number is
outside this project's control, is not part of any contract, and the measurement
above was taken against skills with no referring profiles — the collector's
share may differ once related rows exist. A Django upgrade could change it and
fail a test about `SkillAdmin`.

**C — drop the query-count test.** `test_get_deleted_objects_counts_a_profile_referring_to_several_selected_skills_once`
(`:145-163`) already covers the correctness half of F-4/F-6. Cost: the
non-scaling guarantee — the explicit second half of T079 and a stated Decision
Outcome in `docs/adr/skill-is-the-only-deletable-record.md` — would then be
recorded only in prose.

No recommendation offered, per the persona.

## Observations / Learning Notes — no action needed

**O-1 — the suite currently reports one failure in this working tree, and it is
a stale test schema, not a defect.**
`docker-compose exec web pytest profiles/tests/models/test_skill.py
profiles/tests/admin/test_skill_admin.py` → **1 failed, 33 passed**;
`test_skill_case_insensitive_name_uniqueness_enforced_at_database_level` reports
`DID NOT RAISE IntegrityError`. Cause: `pytest.ini` runs `--reuse-db
--no-migrations`, so the test database still carries the schema built before
`skill_unique_name_case_insensitive` existed. Re-running with `--create-db`
gives **17 passed** on `test_skill.py`. Worth knowing before T065 compares
against the T004 baseline — the failure would read as an SC-009 regression and is
not one. CI creates a fresh database and is unaffected.

**O-2 — answering the question asked: both self-exclusion tests are justified,
despite failing on the same production line.**
`test_skill_whose_name_did_not_change_passes_validation` (`:100`) and
`test_skill_recased_in_place_is_stored_with_the_new_capitalization` (`:108`) do
both die if `.exclude(pk=self.pk)` is deleted. They are still two tests, on three
grounds. (1) `testing.md`'s granularity rule is about behaviors, not production
lines: "re-saving an unchanged skill is accepted" and "recasing in place is
accepted **and stored as typed**" are two behaviors, and both are named
separately in the Phase 10 *do not reopen* block and in the ADR's closing
paragraph. (2) The recasing test additionally guards the never-normalize
decision — introduce any capitalization rule in `clean()` and it fails while the
unchanged-name test does not. (3) The exception to the granularity rule requires
shared *expensive* setup; here setup is one row, so there is no grouping
argument either way. Keeping both is correct.

**O-3 — the `protected` assertions match on a substring of the count.**
`assert "3" in protected[0]` (`:141`) and `assert "1" in protected[0]` (`:163`)
would also pass on `13` or `31`. They discriminate correctly for the current
message, which contains no other digits, and the alternative — asserting the
rendered sentence — would put a translatable message string in an assertion,
which `testing.md` discourages for `ValidationError` and which the same file's
spirit extends here. Noted, not a finding.

**O-4 — the docstring review (audit item 4) found nothing to act on.** Measured
against the *What belongs in a docstring* rule added in `f38123a`:

- `Skill.clean()` (`skill.py:104-117`) — describes behavior throughout,
  including the two clauses that could have drifted into rationale ("kept as
  entered", "left out of the comparison"). Passes. Minor: the summary line
  "Enforce skill validation invariants" is more generic than the
  `Enforce <invariant description>` shape the same file prescribes.
- `SkillAdmin.get_deleted_objects()` (`admin.py:54-69`) — the first two
  sentences are near-verbatim the *Accepted* example in `conventions.md`. The
  trailing clause naming the delete view and the delete selected action is
  borderline framework description; it states an effect rather than justifying a
  choice, so it stays on the right side.
- `SkillAdmin._count_referring_profiles()` (`admin.py:83-95`) — "one aggregate
  query each" is an implementation detail, but it is also a pinned contract (the
  test in OD-1 exists for it), so it reads as behavior.
- `Skill.Meta` carries no docstring; neither does any other `Meta` in
  `profiles/` or `accounts/`. Consistent, not a gap.
- The `skill` fixture in `profiles/tests/conftest.py:112-121` explains
  `--no-migrations` inside its docstring, which the new rule would place in a
  convention file instead. Untouched by Phase 10 and outside this audit's file
  set; recorded only so it is not mistaken for compliance.

**O-5 — `logger.debug("Skill name validation successful")` (`skill.py:159`)
sits outside the `if self.name is not None` block**, so a `None` name logs a
success it never validated. Cosmetic, pre-existing, no PII exposure.

**O-6 — the migration is exactly what T075 gated for.** `0007_…` contains a
single `AddConstraint` and nothing else; no `AlterField`, so `unique=True`
survived on the field as the *do not reopen* block requires. Dependency on
`0006_clientprofile` is correct.

**O-7 — GDPR.** Nothing under audit logs a name or any value. `clean()`'s two
`logger.error` calls describe the violation without the value, matching the
*Logging pattern* convention. The refusal message counts profiles and never
enumerates them, per FR-028 and the ADR.

**O-8 — consistency with `test_freelancer_profile.py`.** The new tests match the
sibling file where it counts: the assertion-free "passes validation" shape
(`test_freelancer_profile_optional_fields_can_be_omitted:232`,
`…creation_accepted_for_active_account:306`), the mutate/`full_clean()`/`save()`/
`refresh_from_db()`/assert shape (`…edit_accepted_on_deactivated_account:316`),
and the two-step `error_dict` assertion. Naming diverges slightly — the sibling
prefixes every test `test_freelancer_profile_*`, while `test_skill.py` mixes
`test_skill_*`, `test_skill_clean_*` and sentence-style names
(`test_skill_whose_name_did_not_change_…`). Both read well; no rule covers it.

**O-9 — what the coverage sweep found that is *not* a gap.** Three members of
`skill.py` are untested and should stay that way, recorded so the next session
does not file them:

- `Meta.db_table = "skills"`, `Meta.verbose_name`, and the `category` field's
  `max_length` / `choices` metadata. Nothing anywhere in `profiles/tests/` or
  `accounts/tests/` asserts a `db_table` or a `verbose_name`, so there is no
  practice to follow — unlike `max_length`, which the project does test (Issue
  7). Rejecting an off-choice `category` is Django's `choices` validator, not
  project code.
- The `Category` vocabulary — the four members TECHNOLOGY / DESIGN / WRITING /
  MARKETING — is asserted by no test. It is used as a value in `test_skill.py`,
  `test_skill_admin.py` and `test_freelancer_profile.py`, so deleting a member
  breaks tests incidentally rather than by intent. `ARCHITECTURE.md` (*Skill —
  Controlled Vocabulary*) records the four as a deliberate replacement for an
  earlier TECHNICAL / LANGUAGE / SOFT taxonomy, so there is a domain decision
  here — but no convention in this project tests a choices vocabulary, so this
  is a note, not a finding.

**O-10 — the inheritance chain, read on the second pass.** `Skill` extends
`models.Model` directly and has no abstract base, so `CLAUDE.md` Rule 2's
read-across-the-chain requirement is satisfied by `skill.py` alone. The chain
that *does* bear on this audit is the one behind `admin.py`:
`FreelancerProfile` and `ClientProfile` both inherit `Profile`
(`profiles/models/base.py`). Reading all three confirms the guard rather than
changing a finding — **neither `FreelancerProfile.skills` nor
`ClientProfile.interests` declares a `related_name`**, so the default
`freelancerprofile_set` / `clientprofile_set` accessors the superseded T013
implementation used do exist today. That is exactly why the ADR's claim holds:
filtering forward from the profile models keeps the count working if a
`related_name` is added to either relation later, which would silently break the
reverse-accessor form.

Recorded so the audited surface is not re-walked next session.

- `clean()` ordering: strip → empty → duplicate, so FR-003 precedes FR-002, per
  T073.
- `.exclude(pk=self.pk)` with `pk is None`: Django rewrites `pk=None` to
  `pk__isnull=True`, which excludes nothing — the unsaved path is unaffected.
- Non-tautology of every **new** test, checked by mentally deleting its target
  line: removing the duplicate block turns the case-variant test's error into a
  `__all__` constraint error (key assertion fails) and the exact-duplicate test's
  code into `unique`; removing the strip breaks the padded-name test; removing
  the `Meta` constraint breaks the database-level test; removing
  `.exclude(pk=self.pk)` breaks both self-exclusion tests.
- `full_clean()` over `clean()` in the new tests is the right choice: the
  duplicate-code assertions depend on `full_clean()`'s ordering — `clean()`
  raising first is what makes `unique` unreachable, which is the contract §4
  documents and the exact-duplicate test now asserts.
- `@pytest.mark.django_db` placement across the whole of `test_skill.py`,
  including the two deliberate omissions (see Issue 5).
- The `.distinct()` on the `FreelancerProfile` aggregate **is** covered
  (`test_skill_admin.py:145`); only the `ClientProfile` half is not (Issue 3).
- Import direction in `admin.py`: profile models come from `profiles.models.*`,
  never from `profiles.admin` (R-001).
- Type hints on every new signature; `django_assert_num_queries` correctly left
  unannotated as a pytest-django built-in.
